# Outage runbook: what the system shows, what staff do

Source of truth: HH-NFR-03 (fallbacks and the runbook responses of guide 29.4), T12, T13, T61, T71, RULE-SAFETY-GATES. Built by TSK-0106. Hosting is one Render web service with Render PostgreSQL (INT-Render); email is Resend, texts are Bird, files are Cloudflare R2.

Labels: FACT (in the code and covered by a test named below), PROPOSED (a choice no owner decision covers), NOT BUILT (the workflow does not exist yet; the task that builds it is named), OWNER ITEM.

## Rule for every outage
Nothing is ever shown as done that did not happen: no receipt without a saved request, no "sent" without the provider's acceptance, no "ready" photo before processing, no start, payment or close that was not recorded. What was saved stays saved, and a retry after recovery takes effect exactly once (idempotency keys on every write and every provider call). When the server cannot check authorization or a gate, nothing unsafe proceeds (RULE-SAFETY-GATES).

## Where to look first
1. **Owner → System health** (staff app): job queue age, failed jobs, failed deliveries, callbacks, photos, and the configuration of each provider (TSK-0101). Backups and the restore drill show as `unknown`: the system cannot observe them (they live in Render and in this folder).
2. **Staff action queue**: every failed automatic message is a `delivery_failed` item with **Retry** (T12).
3. **Render dashboard** (owner): service events, deploy log, the service log (search `API_INTERNAL_ERROR`, `PAGE_ERROR`), database status.
4. The provider's own status page and dashboard (Resend, Bird, Cloudflare).

## Failures and responses

| Failure | What the system does (FACT unless marked) | What staff do | Evidence |
| --- | --- | --- | --- |
| **Email provider (Resend) refuses connections or answers 5xx/429** | The request or business event is saved and its message queued. The send is retried automatically under the same idempotency key; after the last attempt the delivery shows **failed** with its reason (for example `connect_econnrefused`, `http_503`) and opens one `delivery_failed` item. Never audited as sent. | When Resend is back, press **Retry** on the item: it sends exactly one message; a second Retry is refused. If the customer must hear sooner, use another verified contact under policy (staff reply, HH-COM-08). | `outages.test.ts` "Resend refuses connections"; `request-receipt.test.ts` T12 suite |
| **Email provider never answers (timeout, dropped connection)** | Outcome unknown: the provider may have sent it. Shown as failed `outcome_unknown_<code>`, **no Retry** (refused with `OUTCOME_UNKNOWN`), never retried blindly. | Look the message up in Resend's dashboard by time and recipient. If Resend shows it delivered, nothing to do. If Resend has no record, send the customer the information by a staff reply. Never resend blindly. | `outages.test.ts` "Resend never answers"; `request-receipt.test.ts` |
| **Text provider (Bird) down** | Same model as email: retried under the same key; failed with its reason after the last attempt; a STOP is always honoured; never shown as delivered without Bird's status webhook. | Retry from the item when Bird is back, or reach the customer by email. Production texting is off until A2P 10DLC is approved (OQ-BIRD-10DLC). | `outages.test.ts` Bird suite; `delivery-states.test.ts` |
| **Verification code delivery unavailable** | The code is not shown or sent another way; the customer can ask again later (safe reissue). | Staff-assisted verified recovery only (HH-ID rules). **Never** temporary public access to a project. | `contact-verification.test.ts`, `access-recovery.test.ts` |
| **File storage (R2) unavailable** | A new photo upload fails with a retryable error and stores nothing; the draft, its text and the photos already stored are kept. Processing cannot read the original, so a photo stays in quarantine (processing): never ready, never rejected because of the outage. The request can still be submitted; the receipt reports received, processing and failed photos separately and keeps a capability to resend a failed photo to the same request (T13). | Nothing to do for customers; processing resumes on its own when R2 is back. If storage stays down, check the R2 bucket and its keys in Render (owner). | `outages.test.ts` R2 suite; `photos.test.ts`; `request-receipt.test.ts` T13 |
| **Database unavailable** | Every write fails with a retryable error and no receipt, reference, start, payment or close; `/readyz` reports `database: fail`; no staff session can be opened. The browser keeps the request draft and its idempotency key; resending after recovery saves it once, and a repeat returns the same reference. `/healthz` (liveness, no database) still answers. | Check the database in Render (status, connection limit, plan expiry). Tell customers to try again later. Nothing to reconcile: nothing was half-written (each write is one transaction). | `outages.test.ts` "database refuses connections"; `requests.test.ts` T71; `apps/site/test/request-send.test.ts` |
| **Whole web service down** (deploy failed, crash loop, Render outage) | Nothing answers. A deploy whose migration is refused never starts (the container runs `migrate && serve`). | Owner: roll back to the last good deploy if the cause is the release (see `release.md`), otherwise wait for Render. OWNER ITEM: the real public phone number and email are still placeholders (FACT-PUBLIC-CONTACT), so customers have no fallback contact yet. | `rehearsals.md` steps 5-6 |
| **Payment verification uncertain** (customer says a Square payment failed midway) | Only a staff-recorded verified payment changes a balance; a check is pending until cleared (HH-FIN-09). The balance stays due; nothing is recorded from a customer's statement. | Look in Square. Record the payment once, only when Square shows it. NOT BUILT: the reconciliation queue (TSK-0090) and the full ledger (TSK-0086, TSK-0087); until then the owner keeps uncertain cases in Square's own records. | `deposits.test.ts`; T61 stays open until TSK-0090 |
| **Unknown refund outcome** | NOT BUILT (refunds: TSK-0089). | No blind retry; reconcile with Square's record and write down the resolution. | — |
| **Maps** | No maps API is used: the packet shows the address with a plain directions link (OWN-DEC-119, OWN-DEC-121). A maps outage changes nothing in HandyHub. | Use another maps app with the shown address. | `job-packets.test.ts` |
| **Scheduling conflict** | Reservations are checked on the server; a conflict is refused with alternatives; the existing commitment stays (no last-write-wins). | The dispatcher picks an alternative. | `capacity.test.ts`, `window-offers.test.ts` |
| **Authorization or a gate cannot be checked** (server error, offline) | The Start Work gate is evaluated on the server only; without a server answer nothing starts. Offline packets and the sync queue are NOT BUILT (TSK-0079, TSK-0080). | Workers do not start, resume or close work without the online gate. Call the owner; Call 911 for emergencies. | `start-work.test.ts`; `apps/staff/test/StartWork.test.tsx` |
| **Stale packet** | The packet carries its version; a worker acknowledges the version shown; a newer version invalidates readiness (TSK-0072). The offline stale-packet warning is NOT BUILT (TSK-0079). | Refresh the packet before work. | `packet-acknowledgments.test.ts` |
| **Critical hazard or scope change** | NOT BUILT: Stop Work and critical holds from the field (TSK-0077), change orders (TSK-0081). Hard holds set by staff block the Start Work gate (TSK-0074). | Stop, refresh the packet, escalate to the owner; no blind resume. | `start-work.test.ts` |
| **Lost or stolen worker phone** | Staff sessions are server sessions; disabling a member revokes them at once; MFA is mandatory. | Owner: Staff management → disable the member (or reset MFA), then re-enable after recovery. Offline copies (when built) have acknowledged limits. | `staff-management.test.ts`, `staff-mfa.test.ts` |
| **Compromised privileged account** | Same controls; the audit log keeps every privileged action. | Keep evidence (do not delete logs), disable the account, reset password and MFA, review the audit log and exports since the suspected time, then follow the privacy response (attorney packet A-10). | `audit-log.test.ts` |
| **Restore needed** | See `restore.md`: isolated restore, integrity checks, deletion and suppression replay, provider reconciliation, controlled resume. | Owner with Claude; never over live transactions as a routine rollback. | `restore-rehearsal.test.ts` |

## After any outage
- Clear the `delivery_failed` items (Retry or resolve) and check System health shows no failed jobs.
- Provider reconciliation: compare messages marked `outcome_unknown` with the provider's dashboard before anything is sent again.
- Write a short note of what happened and when (PROPOSED: in the project notes or the owner's log; there is no incident register in the app yet).

## Known gaps (remaining deficiencies)
- T61 (payment uncertain → reconciliation queue) is not satisfiable until TSK-0086, TSK-0087 and TSK-0090 exist.
- An unreachable database answers `500 INTERNAL` (retryable) rather than `503 UNAVAILABLE`; both are truthful failures with a retry, but the code could be clearer. RECOMMENDATION: map connection errors to `UNAVAILABLE` in a later change.
- There is no paging or alerting outside the app (no error tracker is configured; System health shows it as not configured). The owner learns of an outage from the app, Render's emails or customers.
- The health check Render polls (`/healthz`) does not touch the database by design; a database outage does not restart the service, it shows as `/readyz` not ready.
