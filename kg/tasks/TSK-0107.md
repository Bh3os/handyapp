Goal: Prove transaction boundaries hold under races, stale versions, duplicates, provider reordering, interruptions and zone edges, and that no automation decides what people must.

Scope:
- Concurrency tests for submission, approval, confirmation, start, sync and payments; provider callback reordering; interrupted transactions.
- Automation audit: no consumer approves, waives, reprices, confirms capacity, decides coverage or refunds.

- Suite runs in CI and passes.
- The `tested_by` scenarios pass for this slice; tests are tagged with the `implements` IDs.
- CI green: `secrets`, `test` (lint, typecheck, unit, integration) and `e2e`.
- Graph: this task set to `status: done`; `node tools/kg.mjs index && node tools/kg.mjs lint` reports 0 problems.

Notes (2026-10-26, built on the merge-queue tip of PR #150; no migration):
- Two real defects found and fixed, each in its own commit with its test:
  - The server did not survive a PostgreSQL restart: a `pg` pool without an 'error' listener ends the Node process when the server ends one of its connections. `createPool` (`packages/db/src/client.ts`) now listens on the pool and on each client; an idle lost connection is dropped and logged by its code only (`onConnectionLost`), one in use fails its query so its transaction commits nothing. Tests: `packages/db/test/integration/client.test.ts` (idle connections ended and replaced; a transaction whose connection is lost half-way commits nothing) and `apps/server/test/integration/boot.test.ts` (a booted server keeps answering after every backend of its pool is terminated with `pg_terminate_backend`) ([[HH-NFR-03]]).
  - A Resend or Bird status processed before its send committed (the provider calls back while the sending transaction is open, or an attempt crashed after the hand-over and its retry records the same message ID) was ignored for good: the delivery never showed delivered, and nothing that follows a delivered message (estimate and question reminders, the response clock) happened. When a delivery records its provider message ID, the statuses ignored for that ID now apply, oldest first, forward only (`applyEarlierStatuses`, `apps/server/src/modules/notifications/status.ts`). Test: `delivery-states.test.ts` ([[HH-DATA-04]]: ordering is never assumed).
- The suite, `apps/server/test/integration/robustness.test.ts` ([[HH-TEST-03]], [[HH-DATA-04]], [[HH-AUTO-02]]):
  - a write failing at its last statement (a trigger on the outbox insert raises): request submission and a staff write answer a retryable INTERNAL, every table is unchanged except the public submission's rate counter (its own transaction by design), and the retry under the same key succeeds once, then replays ([[T11]]);
  - the database connection ended mid-write (`pg_terminate_backend` of the waiting server process): a retryable error, nothing written, the same pool serves the retry; a client that timed out retries while the first write still runs: one request, the same answer twice, a changed body under the key is IDEMPOTENCY_CONFLICT;
  - four staff writes on one request version at once: one wins, the others STALE_VERSION or CONFLICT, never a 500;
  - every registered automation over a whole fictional business (the staging fresh test data through the server's routes): two workers at once; half of the first attempts crash after their effect (lease taken away before the commit), half of the messages lose the provider's answer to their first hand-over; Resend callbacks newest first and repeated. Then: no job failed or left running; the automations changed only their declared effect tables, never a table people decide (approvals, prices, visits, reservations, holds, starts, payments, allocations, refunds, waivers, cases, consent, deletions); every accepted delivery matches exactly one message the provider holds; every called-back delivery shows delivered once; a STOP recorded after the request was queued suppresses its text at send time ([[T67]]); every event dispatched again creates no job and sends nothing; every finished job run a second time changes no table and hands nothing to a provider ([[T65]], [[HH-ARC-09]]).
- Automation audit, `apps/server/test/unit/automation-audit.test.ts` ([[HH-AUTO-02]]): every registered automation is classified by the kind of its one effect (message, delivery status, file check, expiry, schedule, draft, document, staff queue, record, erasure); a new automation fails the test until it is classified; no declared effect approves, waives, reprices, refunds, charges, confirms capacity or releases a hold.
- Concurrent Start: `start-work.test.ts` gains a double tap under one key, another press and the teammate pressing Start at the same moment: one start per worker, every other answer the stored answer or a refusal (ALREADY_STARTED, or PACKET_CHANGED_SINCE_VIEWED for the teammate: the first start writes a new packet version, which the teammate reviews before starting) ([[T46]]).
