> # 1. PRIMARY INSTRUCTIONS FOR CLAUDE CODE
>
> Implement, integrate, test, and prepare the complete HandyHub customer and staff messaging system.
>
> This is not simply an email-template creation task. Build the complete event-driven notification workflow, integrated with:
>
> - Customer project portal
> - Staff administration portal
> - Request management
> - Estimate creation and approval
> - Appointment scheduling
> - Job management
> - Deposits and invoices
> - Payments and receipts
> - Change orders
> - Customer communications
> - Staff notifications
> - Account security
> - Document storage
> - Message delivery tracking
>
> Reuse the existing application architecture and database schema wherever possible.
>
> Do not create duplicate notification systems or conflicting business rules.
>
> Before implementation:
>
> 1. Inspect the existing messaging system, notification templates, and event handlers.
> 2. Identify already implemented functionality.
> 3. Compare existing behavior against this specification.
> 4. Preserve functionality that already works.
> 5. Implement missing functionality and correct inconsistencies.
> 6. Verify all workflow triggers.
> 7. Run automated integration and end-to-end tests.
> 8. Publish the completed implementation to private staging.
> 9. Present the results, unresolved dependencies, and exact production activation requirements.
>
> Do not activate real customer delivery or use real customer data during staging tests.
>
> All message wording below is approved for implementation as the proposed template content, subject to successful placeholder validation, security review, and owner approval before production activation.

> # 2. GLOBAL MESSAGE DESIGN
>
> All customer emails must use a consistent, professional HandyHub template.
>
> ## Email design
>
> Use:
>
> - HandyHub branding and logo
> - Clean, modern layout
> - Mobile-responsive formatting
> - Professional typography
> - Accessible text contrast
> - Clearly visible primary action button when appropriate
> - Readable plain-text alternative
> - Consistent email footer
> - Verified business contact information
>
> Use this subject convention:
>
> `HandyHub | Message Purpose`
>
> For customer greetings:
>
> `Hi {customerName},`
>
> If the name is missing, use:
>
> `Hello,`
>
> Customer email signature:
>
> `The HandyHub Team`
>
> Staff notification signature:
>
> `HandyHub Staff Notifications`
>
> Do not expose internal employee IDs, system diagnostics, database identifiers, authentication tokens, or unnecessary private customer information.
>
> Never send unresolved placeholders.
>
> Store business contact information as centrally managed configuration rather than hardcoding unknown contact details.
>
> Every message should be clear, friendly, professional, and reasonably concise.
>
> Avoid exaggerated marketing language, misleading commitments, unnecessary urgency, and repeated promotional content.

> # 4. CUSTOMER MESSAGE TEMPLATES
>
> ## MESSAGE 01 — Request Received
>
> **Template ID:** `request_received`
>
> **Type:** Transactional  
> **Trigger:** Customer successfully submits a new request.  
> **Delivery:** Automatic  
> **Recipients:** Customer  
> **Frequency:** Once per successfully created request  
> **Timing:** Immediately after successful submission  
>
> ### Subject
>
> HandyHub | We've Received Your Request #{reference}
>
> ### Body
>
> Hi {customerName},
>
> Thank you for contacting HandyHub!
>
> We've received your request #{reference}. Our team will review the details and get back to you as soon as possible. We aim to respond within one hour during our service hours.
>
> Please note that this is a request confirmation, not a confirmed appointment or final price. We'll confirm any appointment separately with a date and arrival window.
>
> If you have questions or additional details to share, feel free to contact us and reference your request number.
>
> Thank you for considering HandyHub!
>
> The HandyHub Team
>
> ### Trigger conditions
>
> - Request successfully saved.
> - Reference number generated.
> - Customer email available.
> - Submission accepted by the system.
>
> ### Do not send when
>
> - Submission validation fails.
> - Request creation fails.
> - Duplicate submission is suppressed.
>
> ### Additional requirements
>
> - Preserve the receipt even when contact verification is pending.
> - Mark customer contact as unverified until verified through the existing process.
> - Never describe the request as a booking.
> - Use a transactional message, not marketing.
>

>
> **Template ID:** `secure_access_link`
>
> **Type:** Security / transactional  
> **Trigger:** Authorized secure project access requested.

>

> The HandyHub Team
>
> ### Requirements
>
> - Use cryptographically secure access tokens.
> - Tokens must expire.
> - Provide a secure token reissue process.
> - Prevent unauthorized project access.
> - Implement rate limiting.
> - Do not put private job details in the email.
> - Log issuance and redemption events without logging raw tokens.
> - Use the existing authentication and project-access architecture.

> - `{startTime}` — Window beginning
> - `{endTime}` — Window end
> - `{start}` — Reminder window beginning
> - `{end}` — Reminder window end
> - `{zone}` — Reminder time-zone label

> - `{jobNumber}` — Job identifier
> - `{serviceName}` — Approved service description

> - `{receiptNumber}` — Receipt identifier
> - `{receiptLink}` — Secure receipt URL
> - `{paymentNumber}` — Payment reference

> - `{staffMessage}` — Released customer message
> - `{staffName}` — Internal staff recipient name
> - `{staffProjectLink}` — Authorized staff project URL
> - `{receivedDateTime}` — Customer reply timestamp
> - `{projectStatus}` — Current project status

>
> - `{changeDate}` — Email-change date
> - `{changeTime}` — Email-change time
> - `{supportContact}` — Verified customer-support contact
>
> ## Variable validation
>
> The implementation must:
>
> 1. Register all required variables.
> 2. Validate availability before rendering.
> 3. Escape untrusted text to prevent HTML injection.
> 4. Safely render both HTML and plain-text email.
> 5. Validate links against permitted hosts.
> 6. Reject invalid or unresolved URLs.
> 7. Never send literal placeholders.
> 8. Use only approved fallback wording.
> 9. Prevent broken or missing required action links.
> 10. Avoid leaking sensitive values into logging systems.
>
> Do not silently substitute another customer's project or document when a variable cannot be resolved.

- Greeting: "Hi {customerName}," with the customer's first name only. When the first name is missing the greeting is "Hi there," ([[OWN-DEC-158]], the later answer, which replaces the "Hello," of section 2).
